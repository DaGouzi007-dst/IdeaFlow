1. 第三模块的想法目前没有 `project_id`；第四模块按项目读取想法、创建任务，需要先对齐项目归属。
2. 第三模块使用 `/api/ideas` 及其当前字段；第四模块样例使用项目下的想法、`content` 和 `source_message_id`。需要负责人共同确定保留的正式接口和字段，再写适配，不能直接交换 URL 就算联通。
3. 第三模块目前使用 `m-0107` 等演示来源编号和字符串列表；正式来源应与会话、消息模块实际编号一致，并能查回原文。UUID 想法编号本身不是目前的唯一衔接条件。
4. 想法阶段“现在做／以后再说／已放弃”与第四模块决策 `pending/adopted/rejected` 含义需区分，避免两套字段各自维护“是否采纳”。
5. 两套独立演示均默认后端 8000、前端 5173。共同启动前需统一服务、路由和数据访问，或明确开发端口。

## 整体打包恢复后的检查顺序

1. 先获取最新分支，与各负责人核对其提交位置；确认哪些成果合入交付分支，哪些仍保留在个人分支。
2. 检查需要随包提交的源码和文档是否已提交进 Git，并保存各分支及提交历史。包含 `.git`；GitHub 的 Download ZIP 不包含完整 Git 历史，不能替代课程仓库压缩包。
3. 排除依赖目录、运行数据库、缓存、构建产物、密钥、真实私密会话，以及本地多轮探索和备份文件。锁文件、模拟样例和正式文档应保留。本地 Git 另有开发工具自动保存的 `refs/codex/` 快照，其中含历史探索文件；它们没有进入正式分支。未来从确认的分支制作干净 Git 副本，保留正式分支、提交历史及副本的 `.git`，不能直接把本工作目录连同所有本地检查点压缩。当前不删除任何本地快照。
4. 运行各已纳入模块的必要验证，如实记录通过项和未完成项；运行 `python scripts/check_delivery.py` 检查仓库材料和文件边界。
5. 生成候选包后在临时目录解压，核对 `.git`、分支、文件清单和必要启动流程；避免只验证“ZIP 能打开”。
6. 整体包命名为 `7组-第1周-代码仓库.zip`（周次由实际提交范围确认）。由组长最终确认并按课程渠道提交；当前没有生成或发送此文件。

`scripts/check_delivery.py` 只读检查本地仓库，不自动获取远程、不运行其他成员代码、不合并、不推送，也不创建压缩包。检查结果不能替代组员提交完成或全组集成验收。
