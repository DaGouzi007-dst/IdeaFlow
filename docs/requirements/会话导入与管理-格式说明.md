# 会话导入与管理 —— 导入格式说明（v1.1）

负责人：王语晨（第一模块）
状态：v1.1。第 4、5 节随 FastAPI 接口实现（第二阶段）修订为现行约定；字段与《开工方案与接口约定（讨论稿）》及组内《公共数据约定》保持一致。
更新日期：2026 年 11 月 14 日（v1.0 为 2026 年 11 月 8 日）

## 1. 目的与范围

本文档整理第一阶段会话导入功能的格式和边界，是《开工方案与接口约定（讨论稿）》中"会话导入第一版约定"的展开。

- 第一阶段只支持**本组约定的 JSON 导入格式**，不宣称兼容任何产品的原生导出格式。
- 直接粘贴纯文本再自动切分消息，涉及角色识别等不确定处理，安排在后续迭代；本文档只定义 JSON 格式。
- 导入后的数据必须符合组内《公共数据约定》：本模块负责创建项目、会话、消息三类数据，内部编号（`project_id`、`conversation_id`、`message_id`）由后端生成 UUID 字符串，请求方不得自带编号。

## 2. 导入接口与请求体

    POST /api/projects/{project_id}/conversations/import

所属项目由 URL 中的 `project_id` 指定，该项目必须已存在（项目由本模块的创建项目接口生成）。请求体为 UTF-8 JSON：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `title` | string | 是 | 会话标题，非空 |
| `source` | string | 是 | 来源名称，非空。取值建议：`manual`、`paste`、`json_file`、`synthetic`，待全组确认后固化为枚举 |
| `source_conversation_id` | string 或 null | 否 | 原工具的会话编号，仅作来源元数据保存；没有则填 `null`，不能当成本系统的内部编号 |
| `messages` | array | 是 | 消息数组，至少 1 条，按对话先后顺序排列 |

可选查询参数 `overwrite`（布尔，默认 `false`）：见第 4 节规则 6。请求体中不包含 `message_id` 和 `conversation_id`：这两类编号由后端生成，并在响应中返回（响应体含 `conversation_id`、`message_ids` 数组、`imported_count`、`overwritten`）。消息的先后顺序按数组顺序保存。

## 3. 消息对象格式

`messages` 数组中每个元素：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `role` | string | 是 | 只允许 `user`、`assistant`、`system` 三种 |
| `content` | string | 是 | 消息内容，非空；**原样保存**，导入不改写内容 |
| `created_at` | string 或 null | 否 | 原始时间，带时区的 ISO 8601 字符串（如 `2026-11-05T20:05:00+08:00`，兼容 `Z` 结尾的 UTC 写法）；原始记录没有时间时填 `null`，不得编造时间 |

查看接口 `GET /api/conversations/{conversation_id}` 返回的每条消息额外带 `seq`（1 起始，按导入顺序），供检索/溯源模块（第二模块契约中的 `seq` 字段）对齐使用；`message_id` 始终是导入时生成的 UUID，全链路沿用同一编号。

## 4. 校验规则

导入时按以下顺序检查，任一环节失败即返回错误，且不写入任何数据（保证"要么全部导入成功，要么什么都不写"；写入阶段在单个 SQLite 事务内完成）：

1. `project_id` 对应的项目存在，否则 `404`。
2. 请求体是合法 JSON 且字段类型正确，否则 `422`。
3. `title`、`source` 为非空字符串；`messages` 为非空数组，否则 `422`。
4. 每条消息 `role` 取值合法、`content` 非空，否则 `422`，并在返回信息中注明是第几条消息。
5. `created_at` 为 `null`，或能解析为**带时区**的 ISO 8601 时间，否则 `422`。
6. `source_conversation_id` 不为空时，若同一项目下已存在相同来源编号的会话，返回 `409` 并附上已有会话的编号（`existing_conversation_id` 字段），提示用户确认。

规则 6 的现行处理方式（v1.1 明确）：

- 默认：返回 `409`，不做任何写入。
- `?overwrite=true`：**原子替换**——旧会话连同其全部消息在同一个事务内删除，新会话写入；响应中 `overwritten` 为 `true`。
- `source_conversation_id` 为 `null` 的会话不参与查重（没有来源编号可比对），允许重复导入。

未知字段第一阶段直接忽略。第 6 条是**同来源重复处理**，不属于跨工具自动去重；立项报告中"重复导入时避免新增相同消息"的完整规则在第 2 至 3 周迭代中评估实现，当前版本不声称支持。

## 5. 错误返回格式（现行约定）

统一返回 JSON，`detail` 为字符串（404/409）或结构化数组（422）：

- `404`（项目/会话不存在）：`{"detail": "项目不存在：<编号>"}`
- `409`（同来源重复）：`{"detail": "同来源会话已存在（source_conversation_id=…），如需替换请加 ?overwrite=true", "existing_conversation_id": "<已有会话编号>"}`
- `422`（格式或取值错误）：`detail` 为数组，每个元素定位一个问题：

        {"message_index": 3, "field": "role", "issue": "role 取值无效（允许：user、assistant、system）", "received": "tool"}

  - `message_index`：1 起始的消息序号（与"第几条消息"口径一致）；非消息级问题（如 `title` 为空）不带该字段。
  - `field`：出问题的字段名（如 `role`、`content`、`created_at`、`title`；请求体本身不是合法 JSON 时为 `body`）。
  - `issue`：中文原因说明。
  - `received`：收到的原始值（截断到 120 字符），仅供排错。

一次校验报出**全部**问题，不修一个报一个。错误码语义：`404` 项目/会话不存在；`422` 格式或取值错误；`409` 同来源重复。前端可按 `message_index` + `field` 直接渲染错误列表。

## 6. 第一版边界（明确不做）

- 不适配任何产品的原生导出格式；适配工具格式前需先取得经授权的脱敏样本并另行验证。
- `role` 不包含 `tool`、`function` 等扩展取值。
- 不做跨工具自动去重、不做消息级合并。
- 不提供消息的手工创建和编辑接口：消息只由导入产生，保证数据来源单一、可追溯。
- 聚合样例文件（`docs/样例/跨模块样例数据.json`）是全模块联调用的**聚合数据夹具**，不是本接口的请求体，两者格式不同；本接口的请求体格式见第 2 节。
