# IdeaFlow 开工方案与接口约定（讨论稿）

这份方案由组长与 AI 根据已确认的模块分工整理，用于小组讨论。四人的模块分工已确认；技术栈、接口细节和每周交付物以组内确认后的版本为准，不代表第一次组会已作出这些决定。

## 一、第一阶段目标

做一个本地运行的 Web 应用，先演示以下流程：创建项目 → 导入会话 → 搜索并查看原文 → 保存想法 → 创建任务 → 更新进度、阻塞及结果。

每个模块也要能够单独演示：检索可先读取模拟会话；想法可以手动创建；任务可以手动创建，也可以关联已有想法。第一阶段先支持规定的 JSON 导入格式和关键词检索，AI 自动提取、想法关系推荐和 Agent 自动阻塞检测放在基础流程之后评估。这里的 JSON 是本组约定的格式，不宣称直接兼容任何产品的原生导出。

## 二、建议采用的技术方案

- **应用形式：** 浏览器页面 + 本地后端，先支持单机演示。四个人各自在自己电脑运行一份，不表示已经实现多人共享、账号或权限管理。
- **前端：** Vue 3 + JavaScript，使用 Vite 构建。按功能拆分页面和组件，后续视需要引入 Vue Router。
- **后端：** Python + FastAPI，以 HTTP/JSON 提供接口；启动后使用 `/docs` 查看接口说明。
- **数据库：** SQLite，本地数据库文件由后端统一读写；不把运行产生的数据库和私密会话提交进 Git。
- **协作：** 同一个 GitHub 仓库，各自在自己的分支开发，通过 Pull Request 合入 `main`，先同步最新代码并进行基本检查。每个人使用自己的账号和提交身份。

选择这套方案是因为团队可以用 Python 实现数据处理和后续 AI 相关功能，前端与后端边界清晰；FastAPI 能自动生成接口说明，SQLite 无需另装数据库服务。SQLite 每个数据库文件同一时间只允许一个写入者；如果以后需要多人并发共享，再评估迁移到服务端数据库。技术栈仍需全组确认，实际版本在初始化框架时由依赖文件和锁文件统一。

## 三、四个模块的边界

1. **王语晨：会话导入与管理。** 负责项目、会话、消息的创建和查看，解析本组规定的导入格式；保存来源信息及原始消息。
2. **苏靖航：内容检索与来源追溯。** 根据项目搜索消息，返回消息所属会话及原消息编号；接入前可用样例数据独立演示。
3. **胡翔：想法提取与整理。** 创建和编辑想法，支持手动创建、从消息创建及回看出处；先用样例消息接入。
4. **唐逸飞：决策与任务跟踪。** 记录想法的采用状态和理由，支持手动创建任务或从想法创建任务，记录进度、阻塞及结果；先用样例想法独立开发。

公共框架和接口协调建议由唐逸飞牵头，四人共同确定和维护；每个模块仍由各自负责人实现并测试。这个安排待小组确认，工作量不合适时可以调整。

## 四、公共数据约定

采用 UTF-8 JSON 和 `snake_case` 字段名。内部编号建议使用 UUID 字符串，创建时生成一次，修改内容不更换编号；导入工具的原始会话编号作为来源元数据单独保存，不能当成本系统的内部编号。由后端创建正式数据时分配编号；离线样例使用预先生成的固定 UUID，仅用于联调。

- **项目**：`project_id`、`name`。由会话管理模块创建。
- **会话**：`conversation_id`、`project_id`、`title`、`source`、`source_conversation_id`。`source` 是来源名称，`source_conversation_id` 是原工具会话编号，没有时填 `null`。
- **消息**：`message_id`、`conversation_id`、`role`、`content`、`created_at`。`role` 为 `user`、`assistant` 或 `system`；`created_at` 是带时区的 ISO 8601 字符串，原始时间缺失时填 `null`。消息属于哪个项目通过会话确定。
- **想法**：`idea_id`、`project_id`、`title`、`content`、`source_message_id`。手动创建时 `source_message_id` 可为 `null`，从消息创建时引用原消息编号。
- **决策**：`decision_id`、`project_id`、`idea_id`、`status`、`reason`。第一版一个想法至多保留一条当前决策，`status` 为 `pending`、`adopted`、`rejected`；未填写理由时 `reason` 可为 `null`。决策归任务跟踪模块，想法数据本身不另存一套决策状态。
- **任务**：`task_id`、`project_id`、`idea_id`、`title`、`description`、`assignee`、`status`、`block_reason`、`resolution`、`result`。`idea_id` 可为 `null`，表示手动创建；`assignee` 第一版为姓名文本或 `null`；状态为 `todo`、`in_progress`、`blocked`、`done`；未填写的阻塞、处理和结果字段为 `null`。

不同模块引用同一条数据时沿用其内部编号。各实体的编号和引用关系必须对应同一个项目；第一版不定义跨项目引用。涉及多个出处或状态历史的详细设计可在后续补充，先不阻塞本周开工。

## 五、接口草案

以下是协作边界，不表示接口已经实现。统一前缀 `/api`，请求和响应为 JSON；具体请求体、响应体、错误返回和分页由负责人在代码框架中共同补充，所有模块使用一致的约定。

- 会话管理：`POST /api/projects` 创建项目；`POST /api/projects/{project_id}/conversations/import` 导入本组 JSON 格式的会话；`GET /api/conversations/{conversation_id}` 查看会话和消息。
- 检索：`GET /api/projects/{project_id}/search?q=关键词` 返回匹配的消息内容、`conversation_id` 和 `message_id`，用于回到原文。
- 想法：`POST /api/projects/{project_id}/ideas` 创建想法；`GET /api/ideas/{idea_id}` 查看想法及来源消息编号。
- 决策和任务：`PUT /api/ideas/{idea_id}/decision` 设置当前决策；`POST /api/projects/{project_id}/tasks` 创建任务；`GET /api/tasks/{task_id}` 查看任务；`PATCH /api/tasks/{task_id}` 更新状态及记录。

会话导入第一版约定：请求体含 `title`、`source`、可空的 `source_conversation_id` 和 `messages` 数组；每条消息含 `role`、`content`、可空的 `created_at`。所属项目由 URL 的 `project_id` 指定，内部 `conversation_id` 和 `message_id` 由后端生成并在响应返回。重复导入的处理规则另行确定，第一版不能声称已支持跨工具自动去重。

## 六、共同样例和独立验证

共同使用 [跨模块样例数据](样例/跨模块样例数据.json)。样例全部为人工编造；其中两个任务分别覆盖“关联想法”和“手动创建”，可用来检查可空关系。这个文件是各模块联调用的**聚合数据夹具**，不是上面单个会话导入接口的请求体。

本周建议各模块至少完成一次可展示的验证：

- 会话管理：读取一段符合约定格式的模拟会话，能展示标题、角色和消息内容。
- 检索：用关键词“任务状态”找回样例消息，显示内容及会话、消息编号。
- 想法：能查看样例想法的来源消息，并说明手动想法如何不依赖来源。
- 任务：能展示关联想法的任务和手动任务，说明待开始、进行中、受阻、完成的变化及阻塞记录。

先用同一份样例各自验证，再替换为真实后端接口。第一阶段联调通过的标准：导入会话后检索到原消息，从消息创建想法，再从想法创建任务并记录一次阻塞和处理结果，最后能够沿关联回到原消息。
