## 二、高亮逻辑改进

### 2.1 问题一：分词切碎导致高亮断裂

**现象**：搜索"幂等"时，`jieba.lcut("幂等")` 返回 `['幂', '等']`，高亮区间变成 `(7,8)` 和 `(8,9)` 两段，前端显示为两个独立的单字高亮，而非"幂等"整体。

**修改**：`search_service.py` 新增 `_merge_ranges`，在 `build_snippet` 返回前合并相邻或重叠区间。

```python
def _merge_ranges(ranges):
    """合并相邻或重叠的区间。"""
    if not ranges:
        return []
    sorted_ranges = sorted(set(ranges))
    merged = [list(sorted_ranges[0])]
    for start, end in sorted_ranges[1:]:
        if start <= merged[-1][1]:
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return [tuple(r) for r in merged]
```

**效果**：`(7,8)` + `(8,9)` → `(7,9)`，前端高亮完整词组。多词查询（如"JWT Redis"）中间隔着字，不会被误合并。

### 2.2 问题二：短语查询时无关词也被高亮

**现象**：搜"缓存击穿"时，"做**缓存**"和"**缓存击穿**"两处都被高亮。原因是高亮按 jieba 分词结果逐词匹配，而"缓存"在原文出现两次。

**修改**：`build_snippet` 增加 `phrase` 参数，**整串优先匹配**——如果完整查询串能在原文连续找到，只高亮这一处；否则退化为逐词高亮。

```python
def build_snippet(content, words, phrase=""):
    # ① 短语优先
    if phrase:
        pos = _positions(content, phrase)
        if pos:
            s, e = pos[0]
            start = max(0, s - WINDOW)
            end = min(len(content), e + WINDOW)
            return content[start:end], [(s - start, e - start)], start
    # ② 原有逐词逻辑
    ...
```

调用处同步传入：

```python
snippet, hl, start = build_snippet(msg.content, words, phrase=q.q.strip())
```

**效果**：

| 查询 | 改前 | 改后 |
|---|---|---|
| `缓存击穿` | "做**缓存**" + "**缓存击穿**" | 仅 "**缓存击穿**" |
| `JWT`、`幂等` | 单词查询 | 不受影响（整串 == 分词结果） |
| `订单 状态机`（带空格） | 逐词高亮 | 自动退化（连续匹配不到） |

## 三、搜索召回逻辑改进

### 3.1 问题：多词 AND 查询命中过少

**现象**：搜"订单 状态机"返回 0 条。原因是 `build_match` 把查询拼成 `"订单" AND "状态机"`，要求**同一条消息同时含两个词**，而 fixture 里"订单"在 S2-m1、"状态机"在 S2-m2，没有一条同时含两者。

对比：搜"状态机 幂等"能命中 S2-m2，因为该消息同时含这两个词。

### 3.2 修改：AND 无结果时降级为 OR

**`retriever.py`**：

```python
def build_match(q, op="AND"):
    words = [w for w in jieba.lcut(q) if re.search(r"\w", w) and w.upper() != "OR"]
    if not words:
        return ""
    return f" {op} ".join(f'"{w}"' for w in words)

class KeywordRetriever:
    def search(self, q, limit, op="AND"):
        expr = build_match(q.q, op)
        ...
```

**`search_service.py`**：

```python
words = [w for w in jieba.lcut(q.q) if w.strip()]
cands = self.retriever.search(q, limit, op="AND")

relaxed = False
if not cands and len(words) > 1:
    cands = self.retriever.search(q, limit, op="OR")
    relaxed = True
```

### 3.3 两个关键设计点

**① 不改 `q.q`，只传 `op`**

最初尝试过 `q_or = q.model_copy(update={"q": " OR ".join(words)})`，但 `build_match` 会把 `"OR"` 当成普通词，拼出 `"订单" AND "OR" AND "状态机"`，结果更差。**正确做法是保持 `q.q` 原样，只把 `op` 从 `"AND"` 换成 `"OR"`。**

**② 筛选条件不绕过**

`KeywordRetriever.search` 里所有筛选（`project_id`、`session_ids`、`tools`、`roles`）在 SQL 层下推，降级时原样保留，不会因为走 OR 就返回其他项目或工具的结果。

### 3.4 效果

| 查询 | 改前 | 改后 |
|---|---|---|
| `订单 状态机` | 0 条 | ≥1 条（S2-m1 或 S2-m2） |
| `状态机 幂等` | 1 条 S2-m2 | 1 条 S2-m2（AND 有结果，不降级） |
| `JWT`、`幂等`、`缓存击穿` | — | 结果不变 |
| `JWT` + 勾 `Claude` | 0 条 | 0 条（筛选不被绕过） |

### 3.5 建议：响应中增加 `relaxed` 标记

用户搜两个词却看到一堆只含一个词的结果，容易困惑。建议在 `SearchResult` 增加 `relaxed: bool` 字段，降级时为 `True`，前端据此提示：

> 未找到同时包含全部关键词的消息，已为你显示包含任一词的结果。

```python
elif r.precision == "exact":

else:
    # 滚到消息顶部，提示"原文位置可能已变化"
```

**注意点**

- `resolve` 返回 `None` 表示**消息不存在**；`available=False` 表示**消息存在但片段漂移**，两者语义不同
- `char_start/char_end` 传 `None` 不报错，返回整条内容 + `precision="message_only"`

### 3.2 `POST /api/trace/resolve-batch`（破坏性变更）

**变更前**：body 为 `list[SourceRef]`，返回 `{message_id: "ok/missing/drifted"}`。

**变更后**：body 为 `BatchResolveRequest`，返回完整解析结果列表。

**请求**：

```json
{
  "refs": [
    {"projectId": "P1", "sessionId": "S2", "messageId": "S2-m2",
     "charStart": 0, "charEnd": 4, "snippet": "用状态机"}
  ],
  "includeContext": false
}
```

**响应**：

```json
[
  {
    "messageId": "S2-m2",
    "status": "ok",
    "resolved": { "ref": {...}, "excerpt": "用状态机", "precision": "exact", "available": true },
    "context": { "center": {...}, "before": [...], "after": [...] }
  },
  { "messageId": "XX-m1", "status": "missing" }
]
```

**注意点**

- 调用方需同步改 body 结构（当前第三部分出处接口未实现，无实际影响）
- `status` 三态：`ok` / `missing` / `drifted`
- `includeContext=true` 时数据量约三倍，**仅详情页用，列表页关闭**

### 3.3 `init_from_aggregate`（第一部分数据入口）

**用途**：第一部分 `{projects, conversations, messages}` 三表平铺 JSON → 第二部分索引。

**用法**：

```bash
cd backend
python -c "from container import init_from_aggregate; \
           init_from_aggregate('../docs/样例/跨模块样例数据.json')"
```

**字段映射**（`AggregateMapper` 固化）

| 第一部分 | 第二部分 | 说明 |
|---|---|---|
| `conversation_id` | `session_id` | 直接映射 |
| `title` | `session_title` | 直接映射 |
| `source` | `tool` | 直接映射 |
| `project_id` | `project_id` | 从 conversations 关联 |
| 数组顺序 | `seq` | 自动生成 |
| — | `id` | 自生成 `{conversation_id}-m{seq}` |
| — | `content_hash` | 自算 `sha1(content)` |

**注意点**

- 第一部分的 `id`、`seq`、`content_hash` **均未提供**，全部由适配层生成
- `id` 生成规则必须与第三部分存的 `message_id` 一致（见第五节）
- 全量重建，重复调用幂等但耗时

### 3.4 `LocalSource.get_window`（兼容性）

**变更**：`seq` 允许为 `None`。

- `seq` 有值 → 邻域取前后各 N 条（原行为）
- `seq=None` → 取会话前 N 条，**不做邻域**（新增降级）

**用途**：第三部分若缺 `seq`，`get_context` 不抛异常，退化为部分上下文。

## 四、对接第三部分：`SourceRef` 序列化约定

**推荐做法**：两端都用 Pydantic 序列化，字段名自动对齐。

```python
# 第三部分写入 IdeaSource.source_ref
source_ref = SourceRef(...).model_dump_json(by_alias=True)   # camelCase JSON
quote = ref.snippet

# 第三部分读取后调用第二部分
ref = SourceRef.model_validate_json(row.source_ref)
r = trace.resolve(ref)
```

**注意点**

- **不要手工拼 JSON**，字段名（camelCase）和可选字段容易出错
- `IdeaSource.quote` 建议存 `SourceRef.snippet`，语义等价，前端可直接展示
- `source_ref` 与 `message_id` 双存时，应保证一致性（建议由写入端从 `message_id` 和其他字段统一生成）
