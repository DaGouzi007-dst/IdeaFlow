# 第二部分 · 接口对接说明

## 一、概述

根据第一、第三部分交付的代码，第二部分做了对接性更新。**核心检索/溯源逻辑未改动**，全部为契约扩展与适配层新增，原有 11 项测试保持通过。

**更新原则**

- 只增不改：已有字段和签名不变，新增字段有默认值
- 适配隔离：第一部分的数据格式差异由 `AggregateMapper` 吸收，第三部分的溯源调用由 `precision` 降级信号兜底
- 零外部调用方：当前无前端/其他部分在调用，破坏性变更成本为零

## 三、接口用法

### 3.1 `POST /api/trace/resolve`（行为增强）

**签名不变**，响应新增 `precision` 字段。

| 字段 | 取值 | 含义 |
|---|---|---|
| `precision` | `exact` | 有偏移且校验通过，前端可直接高亮 |
| `precision` | `message_only` | 无偏移或片段不匹配，只能定位到整条消息 |

**调用示例（第三部分）**：

```python
ref = SourceRef.model_validate_json(row.source_ref)
r = trace.resolve(ref)

if r is None:
    # 消息不存在，展示 row.quote 兜底
elif r.precision == "exact":
    # 高亮 r.excerpt
else:
    # 滚到消息顶部，提示"原文位置可能已变化"
```

**注意点**

- `resolve` 返回 `None` 表示**消息不存在**；`available=False` 表示**消息存在但片段漂移**，两者语义不同
- `char_start/char_end` 传 `None` 不报错，返回整条内容 + `precision="message_only"`

### 3.2 `POST /api/trace/resolve-batch`（破坏性变更）

**变更前**：body 为 `list[SourceRef]`，返回 `{message_id: "ok/missing/drifted"}`。

**变更后**：body 为 `BatchResolveRequest`，返回完整解析结果列表。

**请求**：

```json
{
  "refs": [
    {"projectId": "P1", "sessionId": "S2", "messageId": "S2-m2",
     "charStart": 0, "charEnd": 4, "snippet": "用状态机"}
  ],
  "includeContext": false
}
```

**响应**：

```json
[
  {
    "messageId": "S2-m2",
    "status": "ok",
    "resolved": { "ref": {...}, "excerpt": "用状态机", "precision": "exact", "available": true },
    "context": { "center": {...}, "before": [...], "after": [...] }
  },
  { "messageId": "XX-m1", "status": "missing" }
]
```

**注意点**

- 调用方需同步改 body 结构（当前第三部分出处接口未实现，无实际影响）
- `status` 三态：`ok` / `missing` / `drifted`
- `includeContext=true` 时数据量约三倍，**仅详情页用，列表页关闭**

### 3.3 `init_from_aggregate`（第一部分数据入口）

**用途**：第一部分 `{projects, conversations, messages}` 三表平铺 JSON → 第二部分索引。

**用法**：

```bash
cd backend
python -c "from container import init_from_aggregate; \
           init_from_aggregate('../docs/样例/跨模块样例数据.json')"
```

**字段映射**（`AggregateMapper` 固化）

| 第一部分 | 第二部分 | 说明 |
|---|---|---|
| `conversation_id` | `session_id` | 直接映射 |
| `title` | `session_title` | 直接映射 |
| `source` | `tool` | 直接映射 |
| `project_id` | `project_id` | 从 conversations 关联 |
| 数组顺序 | `seq` | 自动生成 |
| — | `id` | 自生成 `{conversation_id}-m{seq}` |
| — | `content_hash` | 自算 `sha1(content)` |

**注意点**

- 第一部分的 `id`、`seq`、`content_hash` **均未提供**，全部由适配层生成
- `id` 生成规则必须与第三部分存的 `message_id` 一致（见第五节）
- 全量重建，重复调用幂等但耗时

### 3.4 `LocalSource.get_window`（兼容性）

**变更**：`seq` 允许为 `None`。

- `seq` 有值 → 邻域取前后各 N 条（原行为）
- `seq=None` → 取会话前 N 条，**不做邻域**（新增降级）

**用途**：第三部分若缺 `seq`，`get_context` 不抛异常，退化为部分上下文。

## 四、对接第三部分：`SourceRef` 序列化约定

**推荐做法**：两端都用 Pydantic 序列化，字段名自动对齐。

```python
# 第三部分写入 IdeaSource.source_ref
source_ref = SourceRef(...).model_dump_json(by_alias=True)   # camelCase JSON
quote = ref.snippet

# 第三部分读取后调用第二部分
ref = SourceRef.model_validate_json(row.source_ref)
r = trace.resolve(ref)
```

**注意点**

- **不要手工拼 JSON**，字段名（camelCase）和可选字段容易出错
- `IdeaSource.quote` 建议存 `SourceRef.snippet`，语义等价，前端可直接展示
- `source_ref` 与 `message_id` 双存时，应保证一致性（建议由写入端从 `message_id` 和其他字段统一生成）

## 五、待确认事项（阻塞项）

| # | 事项 | 影响 | 建议 |
|---|---|---|---|
| 1 | **`message_id` 两边格式是否一致** | 对不上则 `resolve` 返回 `None`，溯源全断 | 必须三方确认；若不一致，写入端做转换或第二部分加模糊匹配兜底 |
| 2 | **`source_ref` 的 JSON 格式** | 手工拼 JSON 易出错 | 约定两端统一走 Pydantic 序列化 |
| 3 | **`quote` 写入时机** | 影响"新建想法卡片"流程设计 | 建议：创建卡片时调 `resolve` 一次，从原文抄入 |

第 1 条最紧急，建议下次对接会优先确认。

## 八、注意事项速查

| 事项 | 提醒 |
|---|---|
| 批量接口是破坏性变更 | 通知所有调用方改 body 结构 |
